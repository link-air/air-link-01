# tools/ · 发布前工具

两个脚本 + 一份豁免清单，**只用标准库**（和主项目一样零依赖）。放在库里而不是开发机上，
理由只有一个：**发布前那次检查得能被别人重跑**。

| 文件 | 干什么 | 怎么用 |
|---|---|---|
| `prepublish_check.py` | 开源前自检 / 脱敏扫描：密钥（**连全部提交历史一起扫**）、个人绝对路径、联系方式、不该入库的实体、中文文件名、大文件、i18n 覆盖（死键 / 缺译 / 没走 `t()` 的中文）、Python 3.11 语法、README 里的测试数 | `python tools/prepublish_check.py --history`<br>有 error 退出码 1（可进 CI / 钩子）；<br>`--all` 连未跟踪文件一起扫；`--json 报告.json`；<br>`--write-example` 从本机 `config.local.json` 生成 `config.example.json`（值全部清空） |
| `module_index.py` | 从各模块头的「模块速查」块 + AST 生成**接口总表** `docs/modules.md` | `python tools/module_index.py`（重新生成）<br>`python tools/module_index.py --check`（对账，漂了退 1——CI 用） |
| `i18n_allow.txt` | i18n 豁免清单：**确认不是缺口**的初始中文（JS 会覆盖 / 故意不翻）。一行一条，`#` 后写理由 | 改动的是纯文本，`prepublish_check.py` 读取它 |

## 为什么这些检查长这样

- **密钥扫历史**：删掉文件不等于清干净——`git rev-list --objects --all` 里那个 blob 还在。
  脚本对每个文本 blob 跑一遍密钥规则，命中就报出它出现在哪些提交。
- **i18n 三条**：① 字面量读点有没有词条（缺译）；② 词条有没有读点（死键）；
  ③ **有没有中文没走 `t()`**（英文模式会露中文的真缺口）。第 ③ 条最容易误报，
  所以豁免要写进 `i18n_allow.txt` 并写明理由，而不是把规则改松。
- **`--check` 而不是"顺手重写"**：`docs/modules.md` 是生成物，CI 只对账、不自动改文件——
  生成物被 CI 悄悄改掉，人和 diff 都会失去判断力。

## 已知的取舍（写下来，免得当地雷）

- 密钥规则认"值附近有 `test` / `fake` / `mask` / `•`"就放行（测试夹具大量长这样）。
  真 key 误粘进测试时正则救不了——那要靠人眼，脚本只负责把**大部分**情况摆出来。
- i18n 第 ③ 条只做静态近似：JS 里拼出来的字符串（不是字面量）它看不见。
- `module_index.py` 靠模块头的「模块速查」块——**没有那块就列不出接口**，
  这是故意的：那块本来就是本项目的书写纪律（见 `设计与实现对照-结构.md` §四）。
